## Question 1: Pass-the-Hash vs. Net-NTLMv2 Captured Hashes

### Question Text
> "Pass-the-Hash attacks work with Net-NTLMv2 hashes captured from network traffic."

### Question Metadata
- **Type:** `boolean` (True / False)
- **Points:** 8 / 8
- **Difficulty:** Fundamentals

### Answer Options & Platform Feedback
1. `True`:
   * *Feedback:* "Net-NTLMv2 hashes are challenge-response artifacts that must be cracked or relayed, not passed."
2. `False` [CORRECT]:
   * *Feedback:* "Pass-the-Hash requires NT hashes from memory or databases, not Net-NTLMv2 hashes from network captures."

### Verified Answer
**`False`**

### Technical Deep Dive & Pedagogical Explanation
- **The Core Misconception:** Many junior penetration testers conflate an **NT (NTLM) Hash** with a **Net-NTLM (v1/v2) Hash**.
- **NT Hash:** A 32-character hexadecimal string generated by $\text{MD4}(\text{UTF-16LE}(\text{Password}))$. It is stored statically in the SAM database, LSASS process memory, and `ntds.dit`. In the NTLM challenge-response protocol, the server sends a challenge, and the client encrypts that challenge using the **NT Hash directly as the cryptographic key**. Because the plaintext password is never used in the handshake, **Pass-the-Hash works exclusively with NT hashes**.
- **Net-NTLMv2 Hash:** A dynamic, session-bound response generated on the wire when an authentication handshake occurs (e.g., captured via Responder). The client computes an HMAC-MD5 of the NT hash combined with the username, target domain, server challenge, and client nonce. Because the challenge changes on every authentication attempt, **a Net-NTLMv2 hash CANNOT be passed to authenticate to another service**. It must either be:
  1. **Cracked offline** using Hashcat (`mode 5600`) or John the Ripper (`--format=netntlmv2`).
  2. **Relayed in real-time** to another machine that does not require SMB Signing (NTLM Relay attack via `ntlmrelayx.py`).

## Question 2: Credential Exposure in Version Control (Git History)

### Question Text
> "Deleting a password from a config file in the newest commit fully removes it from the repository."

### Question Metadata
- **Type:** `boolean` (True / False)
- **Points:** 8 / 8
- **Difficulty:** Fundamentals

### Answer Options & Platform Feedback
1. `True`:
   * *Feedback:* "The earlier commit that introduced the password still contains it, so it stays recoverable."
2. `False` [CORRECT]:
   * *Feedback:* "Removal only changes the current state; the secret persists in history and must also be rotated."

### Verified Answer
**`False`**

### Technical Deep Dive & Pedagogical Explanation
- **Git Object Model:** Git is an immutable, content-addressable directed acyclic graph (DAG) of commit objects, tree objects, and blob objects.
- When a developer commits a secret (`config.json` containing API keys or passwords) and pushes it to a repository, that commit creates an immutable blob identified by its SHA-1/SHA-256 hash.
- Making a subsequent commit that deletes the password or deletes `config.json` merely creates a **new commit** where the file is absent in the current working tree. The prior commit—and the exposed secret—remains permanently readable in the repository history via:
  ```bash
  git log -p
  git checkout <earlier_commit_hash>
  ```
- **Remediation Requirement:**
  1. **Immediate Revocation & Rotation:** Treat the credential as instantly compromised; rotate it in the production system.
  2. **History Rewriting:** Purge the secret from all historic commit trees using tools like `git-filter-repo`, BFG Repo-Cleaner, or `git filter-branch`, and force-push (`git push --force --all`) across all branches and tags.

## Question 3: Active Directory Protocol Roles — Lightweight Directory Access Protocol (LDAP)

### Question Text
> "Which service does LDAP provide in an Active Directory environment?"

### Question Metadata
- **Type:** `single-choice`
- **Points:** 8 / 8
- **Difficulty:** Fundamentals

### Answer Options & Platform Feedback
- `A` - **Transferring files between domain members**:
  * *Feedback:* "File transfer over the network is handled by SMB shares, not the directory protocol."
- `B` - **Querying directory objects such as users and groups** [CORRECT]:
  * *Feedback:* "LDAP gives a central directory that clients query for users, groups, computers and organisational data."
- `C` - **Encrypting all domain logon traffic**:
  * *Feedback:* "Plain LDAP is unencrypted; the secure variant adds TLS but encryption is not its purpose."
- `D` - **Granting remote shell access to a domain controller**:
  * *Feedback:* "Remote shells come from services such as WinRM or RPC-based execution, not directory queries."
- `E` - **Distributing group policy files to workstations**:
  * *Feedback:* "Policy files are pulled from the SYSVOL share over SMB, even though policy objects live in the directory."

### Verified Answer
**`Querying directory objects such as users and groups`**

### Technical Deep Dive & Pedagogical Explanation
- **LDAP Architecture (RFC 4511):** Operates on TCP/UDP port 389 (unencrypted / StartTLS) and TCP port 636 (LDAPS over SSL/TLS).
- LDAP is the hierarchical query protocol of Active Directory. It provides a standardized tree structure (Directory Information Tree - DIT) enabling clients, servers, and administrators to:
  - Query user attributes (e.g., `sAMAccountName`, `mail`, `memberOf`, `userAccountControl`, `servicePrincipalName`).
  - Search group hierarchies and memberships.
  - Locate domain controllers, computers, organizational units (OUs), and Group Policy Object (GPO) metadata.
  - Perform authentication binds (`Simple Bind` or `SASL / GSS-API / Kerberos Bind`).
- In penetration testing, tools like NetExec (`nxc ldap`), BloodHound (`bloodhound-python`), and PowerView use LDAP queries to map domain architecture and identify vulnerable ACLs.

## Question 4: Offline Kerberos Ticket Cracking — Hashcat Modes

### Question Text
> "Which Hashcat mode is used specifically for cracking AS-REP hashes?"

### Question Metadata
- **Type:** `single-choice`
- **Points:** 8 / 8
- **Difficulty:** Intermediate

### Answer Options & Platform Feedback
- `A` - **3200**:
  * *Feedback:* "This mode is for bcrypt hashes, not AS-REP Kerberos hashes."
- `B` - **7500**:
  * *Feedback:* "This mode is for Kerberos 5 AS-REQ Pre-Auth, not AS-REP hashes."
- `C` - **13100**:
  * *Feedback:* "This mode is for Kerberos TGS-REP (Kerberoasting), not AS-REP hashes."
- `D` - **18200** [CORRECT]:
  * *Feedback:* "Mode 18200 is specifically designed for cracking AS-REP Kerberos hashes."
- `E` - **1000**:
  * *Feedback:* "This mode is for NTLM hashes, not AS-REP Kerberos hashes."

### Verified Answer
**`18200`**

### Technical Deep Dive & Pedagogical Explanation
- **Hashcat Kerberos Mode Comparison:**
  - **Mode `18200` (AS-REP Roasting):** Targets accounts configured with `UF_DONT_REQUIRE_PREAUTH`. The attacker captures an `AS-REP` packet containing an `enc-part` encrypted with the user's password-derived NT hash (etype 23 RC4-HMAC).
  - **Mode `13100` (Kerberoasting):** Targets service accounts with Service Principal Names (`servicePrincipalName`). The attacker captures a `TGS-REP` packet containing a service ticket encrypted with the service account's password hash (etype 23 RC4-HMAC).
  - **Mode `1000` (NTLM):** Plain NTLM password hash (`MD4(UTF-16LE(Password))`).
  - **Mode `7500` (Kerberos 5 AS-REQ Pre-Auth etype 23):** Used when intercepting pre-authentication timestamps.
  - **Mode `3200` (bcrypt):** OpenBSD Blowfish password hashing.

## Question 5: Relative Identifiers (RIDs) & Built-in Accounts

### Question Text
> "In a Windows domain, which account is identified by the well-known RID 500?"

### Question Metadata
- **Type:** `single-choice`
- **Points:** 8 / 8
- **Difficulty:** Intermediate

### Answer Options & Platform Feedback
- `A` - **The first user account created**:
  * *Feedback:* "Ordinary user accounts are allocated identifiers starting from 1000 onwards."
- `B` - **Administrator** [CORRECT]:
  * *Feedback:* "RID 500 is the built-in administrator, which is why RID cycling often starts around this value."
- `C` - **Guest**:
  * *Feedback:* "The guest account sits at the next well-known identifier above the built-in administrator."
- `D` - **Domain Admins**:
  * *Feedback:* "That is a group whose well-known identifier falls in the range just above 511."
- `E` - **krbtgt**:
  * *Feedback:* "The Kerberos service account has its own well-known RID, distinct from the built-in administrator."

### Verified Answer
**`Administrator`**

### Technical Deep Dive & Pedagogical Explanation
- **Windows Security Identifiers (SIDs):** Every object in Active Directory possesses an immutable SID in the format:
  $$\text{S-1-5-21}-\langle\text{Domain Identifier}\rangle-\langle\text{RID}\rangle$$
- The Relative Identifier (RID) represents the final sub-authority identifying the specific account or group within the domain:
  - **RID 500:** Built-in **`Administrator`** account (even if renamed to `adm_root` or `john_admin`, its RID remains 500!).
  - **RID 501:** Built-in **`Guest`** account.
  - **RID 502:** Built-in **`krbtgt`** (Key Distribution Center service account).
  - **RID 512:** Built-in **`Domain Admins`** group.
  - **RID 513:** Built-in **`Domain Users`** group.
  - **RID 514:** Built-in **`Domain Guests`** group.
  - **RID 515:** Built-in **`Domain Computers`** group.
  - **RID 516:** Built-in **`Domain Controllers`** group.
  - **RID $\ge$ 1000:** User accounts and custom groups created by administrators.
- **Offensive Significance (RID Cycling):** Attackers exploit RPC MS-SAMR (`lookupsids.py` or `netexec --rid-brute`) by cycling RIDs starting from 500 upwards to discover exact usernames regardless of renaming policies.

## Question 6: Kerberos Credential Cache in Linux Tooling

### Question Text
> "Which environment variable tells Kerberos-aware Linux tooling which credential cache file to use?"

### Question Metadata
- **Type:** `single-choice`
- **Points:** 8 / 8
- **Difficulty:** Intermediate

### Answer Options & Platform Feedback
- `A` - **KRB5_CONFIG**:
  * *Feedback:* "That points at the krb5.conf configuration file, not at a ticket cache."
- `B` - **KRB5CCNAME** [CORRECT]:
  * *Feedback:* "Impacket and MIT Kerberos utilities read this variable to locate the active ccache."
- `C` - **KRBTGT**:
  * *Feedback:* "krbtgt is the KDC service account name, not an environment variable."
- `D` - **KRB5REALM**:
  * *Feedback:* "Realm selection comes from configuration or the principal supplied; this is not the cache pointer."
- `E` - **KRB5_TRACE**:
  * *Feedback:* "That enables verbose Kerberos debugging output and has no effect on cache selection."

### Verified Answer
**`KRB5CCNAME`**

### Technical Deep Dive & Pedagogical Explanation
- **Kerberos on Linux (MIT Kerberos / Heimdal):**
  When Linux tools authenticate via Kerberos, they store tickets (TGTs and service tickets) in binary credential cache files (`.ccache`), typically located at `/tmp/krb5cc_<uid>`.
- The environment variable **`KRB5CCNAME`** specifies the path to the active credential cache:
  ```bash
  export KRB5CCNAME=/path/to/Administrator.ccache
  ```
- **Weaponization in Active Directory Tooling:**
  Impacket tools (`psexec.py`, `wmiexec.py`, `smbexec.py`, `secretsdump.py`), Evil-WinRM (`-r <realm>`), and NetExec automatically check for `KRB5CCNAME` when executed with the `-k` (use Kerberos) and `-no-pass` flags. This enables **Pass-the-Ticket (PtT)** attacks where stolen or forged tickets (such as those minted via `getST.py` during S4U constrained delegation or Golden Tickets minted via `ticketer.py`) are used to execute remote commands without passwords.
