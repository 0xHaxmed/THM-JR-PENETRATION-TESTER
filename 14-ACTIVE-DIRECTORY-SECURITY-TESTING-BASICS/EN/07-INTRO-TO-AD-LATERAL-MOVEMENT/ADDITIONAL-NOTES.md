## 1. Remote Execution Mechanics: Service Control Manager (MS-SCMR)

Impacket's `psexec.py` does not exploit any memory corruption vulnerabilities. It relies entirely on legitimate administrative RPC calls defined in the **Service Control Manager Remote Protocol (MS-SCMR)**:

### Low-Level Execution RPC Sequence:
1. **SMB Session Setup:** Establishes an SMB session to `\\target\IPC$` using valid administrative credentials or an NTLM hash.
2. **File Staging:** Connects to `\\target\ADMIN$` (`C:\Windows\`) and uploads an executable (e.g., `kKjQbvqG.exe`).
3. **RPC Binding:** Binds to the `svcctl` interface over the named pipe `\PIPE\svcctl` using interface UUID `367abb81-9844-35f1-ad32-98f038001003`.
4. **`OpenSCManagerW`:** Requests a handle to the Service Control Manager with `SC_MANAGER_ALL_ACCESS` rights.
5. **`CreateServiceW`:** Creates a service with:
   - `lpServiceName`: Random alphanumeric string (e.g., `ZcMo`).
   - `lpBinaryPathName`: `%SystemRoot%\kKjQbvqG.exe`.
   - `dwServiceType`: `SERVICE_WIN32_OWN_PROCESS` (`0x00000010`).
   - `dwStartType`: `SERVICE_DEMAND_START` (`0x00000003`).
   - `lpServiceStartName`: `LocalSystem` (spawns as `NT AUTHORITY\SYSTEM`).
6. **`StartServiceW`:** Triggers service execution.
7. **Forensic Footprint:**
   - **System Event ID 7045:** Generated by Service Control Manager.
   - **Security Event ID 4697:** Generated if service creation auditing is enabled.
   - **Security Event ID 4624 (Logon Type 3):** Network logon.

## 2. Windows Remote Management (WinRM) & WS-Management Protocol

WinRM is Microsoft's implementation of the open standard **WS-Management (Web Services-Management)** protocol (DMTF standard):

### Protocol Characteristics:
- **Transport:** HTTP (Port `5985`) or HTTPS (Port `5986`).
- **Encapsulation:** SOAP XML envelopes over HTTP `POST` requests.
- **Protocol:** PowerShell Remoting Protocol (**MS-PSRP**).
- **Execution Context:** Unlike PsExec, WinRM executes processes inside the security token of the **authenticated user** (unless explicitly configured with alternate credentials).
- **Forensic Footprint:**
  - Leaves **no executable files on disk**.
  - Creates **no Windows services**.
  - Logs standard network logon (**Event ID 4624 Type 3**).
  - Logs PowerShell execution events (**Event ID 4104 Script Block Logging**).

## 3. Cryptographic Comparison: NT Hash vs. Net-NTLMv2

Understanding the difference between the stored NT hash and the on-the-wire Net-NTLMv2 challenge-response is critical for offensive lateral movement:

```
                  NT HASH vs. Net-NTLMv2 COMPARISON MATRIX
  ┌───────────────────────────────┬───────────────────────────────┐
  │         NT / NTLM HASH        │        Net-NTLMv2 HASH        │
  ├───────────────────────────────┼───────────────────────────────┤
  │ MD4(UTF-16LE(Password))       │ HMAC-MD5(NT_Hash, User||Realm)│
  │                               │ iterated with Server/Client   │
  │                               │ Challenges.                   │
  ├───────────────────────────────┼───────────────────────────────┤
  │ Stored in: SAM, LSASS, NTDS   │ Captured from: Wire via       │
  │                               │ Responder, LLMNR, NBT-NS.     │
  ├───────────────────────────────┼───────────────────────────────┤
  │ Pass-the-Hash: YES (100%)     │ Pass-the-Hash: NO (NEVER!)    │
  ├───────────────────────────────┼───────────────────────────────┤
  │ Format: 32 hex chars          │ Format: Multiline colon-      │
  │ (fa0af7f6a73316dd...)         │ delimited blob with challenge │
  └───────────────────────────────┴───────────────────────────────┘
```

### Mathematical Net-NTLMv2 Derivation:
$$\text{ResponseKeyNT} = \text{HMAC-MD5}\left(\text{Key}=\text{NT\_Hash}, \; \text{Data}=\text{Uppercase}(\text{Username}) \parallel \text{Uppercase}(\text{Domain})\right)$$
$$\text{NTProofStr} = \text{HMAC-MD5}\left(\text{Key}=\text{ResponseKeyNT}, \; \text{Data}=\text{ServerChallenge} \parallel \text{ClientChallenge}\right)$$

Because $\text{ResponseKeyNT}$ is bound to the dynamic challenge, **Net-NTLMv2 hashes cannot be used in Pass-the-Hash attacks**. They must either be cracked offline into plaintext using Hashcat (`mode 5600`) or relayed in real-time to an unhardened service (NTLM Relay).

## 4. SSH SOCKS Pivoting & ProxyChains `connect()` Hooking

When an SSH client executes `ssh -D 1080 user@host`, it creates an internal **SOCKS proxy server** listening on `127.0.0.1:1080` and tunnels traffic over the encrypted SSH channel:

### How ProxyChains Works:
ProxyChains uses the `LD_PRELOAD` environment variable on Linux to intercept standard C library (`libc.so`) networking calls before they reach the kernel:
1. When an application calls `socket()` or `connect(sockfd, &addr, addrlen)`, ProxyChains intercepts the call.
2. ProxyChains redirects the connection to `127.0.0.1:1080`.
3. It performs a SOCKS4/SOCKS5 handshake, instructing the remote SSH daemon on the pivot server to establish a TCP socket to the true target (`192.168.13.100:445`).
4. Once established, data flows transparently through the SSH tunnel.

### Why Nmap SYN Scans (`-sS`) Fail through SOCKS:
- SYN scanning requires crafting raw Layer 3 IP/Layer 4 TCP packets with custom sequence numbers using raw sockets (`AF_INET, SOCK_RAW`).
- SOCKS proxies operate exclusively at the application Layer (Layer 5) and support only standard connection streams (`SOCK_STREAM`).
- Raw packets cannot be sent through a SOCKS proxy; therefore, Nmap must be instructed to use standard OS TCP connect calls via **`-sT`** and disable ICMP ping discovery via **`-Pn`**.

## 5. Enterprise Access Model: Microsoft Tiered Administration

To permanently eliminate lateral movement and credential harvesting risks, Microsoft recommends the **Enterprise Access Model** (formerly known as the Red Forest / Administrative Tiering Model):

```
                     MICROSOFT ENTERPRISE ACCESS MODEL
  ┌────────────────────────────────────────────────────────────────────────┐
  │ TIER 0: Control Plane (Identity & Directory Services)                 │
  │ • Domain Controllers, PKI, ADFS, Entra ID Connect                     │
  │ • Managed strictly via Dedicated Privileged Access Workstations (PAWs)│
  │ • Domain Admins NEVER log into Tier 1 or Tier 2 machines.             │
  ├────────────────────────────────────────────────────────────────────────┤
  │ TIER 1: Management Plane (Enterprise Servers & Workloads)              │
  │ • File servers, SQL databases, Hypervisors, Application servers        │
  │ • Server Admins only. Local passwords managed via Windows LAPS.        │
  ├────────────────────────────────────────────────────────────────────────┤
  │ TIER 2: User Access Plane (Client Endpoints & Users)                   │
  │ • Laptops, Workstations, Mobile devices, Helpdesk                     │
  │ • Workstation-to-workstation (East-West) traffic completely blocked.  │
  └────────────────────────────────────────────────────────────────────────┘
```
**Golden Rule of Tiering:** Credentials from a higher tier must **never** be used on or exposed to a lower-tier machine.
