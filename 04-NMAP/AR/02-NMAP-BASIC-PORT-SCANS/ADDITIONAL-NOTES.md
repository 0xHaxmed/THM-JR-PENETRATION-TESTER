# ملاحظات إضافية وتعمق تقني: فحص المنافذ الأساسي (ADDITIONAL-NOTES.md)

---

### 1. تشريح آلة الحالة لمكدس بروتوكول TCP (TCP State Machine & Handshake Mechanics)
يتبع تبادل حزم TCP في فحص المنافذ القواعد المحددة في معيار RFC 793:
* **في فحص TCP Connect Scan (`-sT`):**
  $$\text{Scanner} \xrightarrow{\text{SYN}} \text{Target} \xrightarrow{\text{SYN-ACK}} \text{Scanner} \xrightarrow{\text{ACK}} \text{Target (ESTABLISHED)} \xrightarrow{\text{RST-ACK}} \text{Target (CLOSED)}$$
  * نظراً لأن حالة `ESTABLISHED` تتحقق على مستوى النواة، تقوم نواة خادم الهدف بوضع الاتصال في طابور `listen backlog` وإشعار التطبيق المستمع عبر إشارة `poll()` أو `epoll_wait()`.
  * يستدعي التطبيق دالة `accept()`، فيحصل على مقبس العميل ويسجل عنوانه في سجلات الوصول التطبيقية (Application Access Logs).

* **في فحص TCP SYN Scan (`-sS`):**
  $$\text{Scanner} \xrightarrow{\text{SYN}} \text{Target} \xrightarrow{\text{SYN-ACK}} \text{Scanner} \xrightarrow{\text{RST}} \text{Target (CLOSED)}$$
  * يظل الاتصال في حالة `SYN-RECEIVED` المؤقتة داخل جدول النواة (Half-Open Queue).
  * قبل أن تنتقل الجلسة إلى `ESTABLISHED` وقبل استدعاء `accept()`، تصل حزمة `RST` وتقوم بإسقاط الجلسة تماماً من الذاكرة دون تمرير أي بيانات للتطبيق، مما يحول دون ظهور الفحص في معظم سجلات الخوادم الكلاسيكية.

### 2. المصفوفة التفصيلية لشروط حالات المنافذ الست في Nmap (The Six Port States Criteria)

```text
+-------------------+---------------------------------------------------+---------------------------------------------+
|    حالة المنفذ    |               الحزم الاستعلامية المرسلة           |              الاستجابة المستلمة من الهدف    |
+-------------------+---------------------------------------------------+---------------------------------------------+
| Open              | SYN (أو UDP probe)                                | SYN-ACK (أو رد UDP من الخدمة)               |
| Closed            | SYN / ACK / Connect                               | RST أو RST-ACK                              |
|                   | UDP Probe                                         | ICMP Type 3 Code 3 (Port Unreachable)       |
| Filtered          | أي نوع حزمة                                       | لا رد على الإطلاق (Timeout) أو:            |
|                   |                                                   | ICMP Type 3 Code 1, 2, 9, 10, 13            |
| Unfiltered        | ACK Probe (في فحص -sA)                            | RST                                         |
| Open|Filtered     | UDP Probe (أو Null/FIN/Xmas)                      | لا رد على الإطلاق (غياب ICMP Port Unreach)  |
| Closed|Filtered   | فحص الخمول (Idle Scan -sI)                        | عجز عن التمييز بين الإغلاق والحجب           |
+-------------------+---------------------------------------------------+---------------------------------------------+
```

### 3. المعمارية الداخلية لتقييد رسائل أخطاء ICMP في نواة لينكس (Kernel Rate Limiting)
* يعود سبب البطء الشديد لفحص منافذ UDP إلى إعدادات النواة المسؤولة عن منع استنزاف الموارد ومنع هجمات الاستطلاع التخمينية:
  * الملف `/proc/sys/net/ipv4/icmp_ratelimit`: يحدد الفاصل الزمني بالمللي ثانية بين رسائل أخطاء ICMP المتعاقبة (الافتراضي عادة 1000 مللي ثانية = ثانية كاملة).
  * الملف `/proc/sys/net/ipv4/icmp_msgs_burst`: يحدد عدد الرسائل المسموح بإرسالها دفعة واحدة قبل فرض التقييد (Burst Limit).
* لذلك، عندما يفحص Nmap منافذ UDP مغلقة، يرسل الحزم وينتظر استلام `ICMP Port Unreachable`. فإذا كانت النواة مقيدة برسالة واحدة في الثانية، يُجبر Nmap على الانتظار وإعادة الإرسال، مما يجعل الفحص الشامل لـ 65,535 منفذ UDP يستغرق ساعات طويلة جداً.

### 4. المحددات التقنية لقوالب التوقيت القياسية (`-T0` إلى `-T5`)

| القالب | الاسم الرمزي | الفاصل الزمني بين الحزم (Delay) | مهلة فحص المنفذ (RTT Timeout) | الحد الأقصى للمحاولات (Retries) | الاستخدام الميداني الموصى به |
|---|---|---|---|---|---|
| `-T0` | Paranoid | 5 دقائق (300 ثانية) | 5 دقائق | 10 محاولات | تجاوز أنظمة كشف التسلل (IDS Evasion) |
| `-T1` | Sneaky | 15 ثانية | 15 ثانية | 10 محاولات | الشبكات الخاضعة لمراقبة SOC صارمة |
| `-T2` | Polite | 0.4 ثانية (400 مللي ثانية) | تكيفي | 10 محاولات | تجنب إسقاط أجهزة إنترنت الأشياء والراوترات |
| `-T3` | Normal | ديناميكي وتكيفي | تكيفي | 10 محاولات | الفحص الافتراضي المتوازن |
| `-T4` | Aggressive | تكيفي سريع (أقل من 10ms) | لا يتجاوز 1.25 ثانية | 6 محاولات | شبكات محلية ممتازة ومسابقات CTF |
| `-T5` | Insane | تكيفي فائق السرعة | لا يتجاوز 0.3 ثانية | مرتان فقط | فحص شبكات داخلية سريعة جداً مع احتمالية خطأ |

### 5. رصد فحوصات SYN في أنظمة كشف التسلل (Snort / Suricata Detection Rule)
تكتشف أنظمة كشف التسلل الحديثة فحص الـ SYN عبر قواعد مثل:
```text
alert tcp $EXTERNAL_NET any -> $HOME_NET any (
    msg:"SCAN Nmap TCP SYN Stealth Scan Detected";
    flags:S;
    flow:stateless;
    threshold:type threshold, track by_src, count 20, seconds 5;
    classtype:attempted-recon;
    sid:1000001; rev:1;
)
```
تقوم القاعدة برصد أي عنوان مصدر خارجي يرسل أكثر من 20 حزمة تحمل راية `SYN` فقط خلال 5 ثوانٍ، وتولد إنذاراً فورياً بتعرض الشبكة لعملية فحص واستطلاع بواسطة أداة مثل Nmap.
