# ملاحظات تقنية متقدمة وهندسية: مكرر بيرب سويت (Burp Suite: Repeater Advanced Notes)

---

## 1. البنية الهندسية الداخلية لوحدة Repeater (Internal Architecture & Socket Management)

### كيفية تعامل Repeater مع اتصالات TCP/TLS:
عندما تنقر على زر **Send** في Repeater، لا يمر الطلب عبر متصفح الويب، بل ينشئ Burp Suite مأخذاً شبكياً مباشراً (Direct TCP Raw Socket) مع الخادم الهدف المحدد في إعدادات `Target`:
1. **حل اسم النطاق (DNS Resolution):** يقوم محرك جافا في Burp بحل النطاق عبر خوادم DNS المحلية للنظام، ما لم يتم تحديد خادم بروكسي في إعدادات `Upstream Proxy`.
2. **مصافحة TLS (TLS Handshake):** إذا كان الهدف `https://`، يقوم Burp بالتفاوض على التشفير (Cipher Suites) وإصدار TLS (مثل TLS 1.3 أو 1.2)، مع إمكانية تجاهل أخطاء الشهادات غير الصالحة تلقائياً.
3. **دفق البايتات (Byte Streaming):** يتم إرسال محتوى لوحة `Request` حرفياً دون أي تعديل خفي، باستثناء التحديث التلقائي لترويسة `Content-Length` إذا تم تفعيل هذا الخيار في قائمة Repeater.
4. **تجميع اتصال Keep-Alive (Connection Reuse):** يتيح تفعيل استمرار الاتصال (`Connection: keep-alive`) إعادة استخدام نفس نفق TCP للطلبات المتتالية، مما يقلل من زمن الانتقال (Latency) عند تكرار إرسال الحمولات.

## 2. إدارة وتحديث ترويسة Content-Length تلقائياً (Auto-updating Content-Length)

في القائمة العلوية لأداة Repeater، يوجد خيار حرج بعنوان:
`Repeater -> Update Content-Length`

```text
[ Manual Payload Tampering ]
              │
              ├──▶ [ Option Enabled (Default) ] ──▶ يقوم Burp بعدّ بايتات جسم الطلب وتحديث ترويسة Content-Length تلقائياً.
              │
              └──▶ [ Option Disabled ]          ──▶ يُرسل الطلب بطول ثابت رغم تغيير الجسم.
                                                     (حرج لاختبار ثغرات HTTP Request Smuggling و CL.TE / TE.CL!)
```

> [!WARNING]
> في العمليات العادية واختبارات حقن المدخلات البسيطة، يجب ترك هذا الخيار مفعلًا. أما عند فحص هجمات تهريب طلبات HTTP (Request Smuggling)، فإن تعطيله أمر إلزامي لصياغة طلبات غير متطابقة الأطوال عمداً.

## 3. تفكيك وتحليل أنماط شريط الرسائل (Message Analysis Engines)

### أ. محرك Pretty:
* يدعم التلوين التلقائي (Syntax Highlighting) لـ HTML و JSON و XML و YAML.
* يوفر إمكانية طي الأقسام (Code Folding) لتصفح استجابات API الضخمة التي تحتوي على آلاف الأسطر.

### ب. محرك Raw:
* يعرض ترويسات HTTP والاستجابة بصيغة ASCII نقية مع إبراز محارف نهاية الأسطر `\r\n`.
* أساسي للتأكد من عدم وجود مسافات بيضاء غير مرئية أو أسطر إضافية تؤدي إلى أخطاء في الخادم (Malformed Requests).

### ج. محرك Hex:
* يقسم العرض إلى ثلاثة أعمدة:
  1. **Offset:** إزاحة البايت الست عشري في دفق البيانات.
  2. **Hex Data:** القيمة البايتية المباشرة (مثل `0D 0A` لـ CRLF، أو `00` للبايت الصفري).
  3. **ASCII Representation:** الرمز المقابل أو نقطة `.` للمحارف غير القابلة للطباعة.
* لا غنى عنه في فحص الملفات المرفوعة لاكتشاف تواقيع الملفات السحرية (Magic Bytes) مثل `89 50 4E 47` لملفات PNG.

### د. محرك Render:
* متصفح مدمج لتصيير صفحات الويب بصرياً.
* يقوم المحرك بتعطيل تنفيذ أكواد JavaScript تجنباً لهجمات XSS التي قد تستهدف واجهة Burp الرسومية أو تنفذ إجراءات غير مقصودة في الخلفية.

## 4. الميكانيكية الرياضية والبرمجية لحقن SQL القائم على الاتحاد (UNION SQLi Mechanics)

### القواعد الصارمة لمشغل UNION:
لكي تنجح عملية دمج نتائج استعلامين عبر `UNION` أو `UNION ALL`:
1. **تطابق عدد الأعمدة (Identical Column Count):** يجب أن يرجع الاستعلام الثاني نفس عدد الحقول التي يرجعها الاستعلام الأصلي.
2. **توافق أنواع البيانات (Data Type Compatibility):** يجب أن تكون أنواع بيانات الأعمدة في الاستعلام الثاني متوافقة تسلسلياً مع أنواع بيانات الاستعلام الأول (مثال: إذا كان العمود الأول نصياً `VARCHAR`، يجب أن يكون العمود المقابل له في `UNION` نصياً أيضاً).

```text
Original Query:
SELECT col1, col2, col3 FROM products WHERE id = 1;

Attacker Injected Query:
SELECT col1, col2, col3 FROM products WHERE id = 0 
UNION ALL 
SELECT 'flag_data', null, null FROM secrets;
```

### كسر نتيجة الاستعلام الأول:
عند استغلال الثغرة في الواجهات التي تعرض سجلاً واحداً فقط (مثل صفحة تفاصيل المنتج أو صفحة الموظف `/about/1`)، إذا أعاد الاستعلام الأول نتيجة صالحة، سيتجاهل التطبيق صفوف الاستعلام الثاني المدمج!
* **الحل التكتيكي:** جعل شرط الاستعلام الأول غير محقق، إما بتمرير معرّف غير موجود مثل `id = -1` أو `id = 0` أو إضافة شرط نفي `AND 1=2`.

## 5. البصمة العملياتية والأثر الأمني (OpSec & Server-side Log Footprint)

* **انعدام التخزين المؤقت (No Cache Headers):**
  غالباً ما تضيف أدوات Burp أو المتصفحات ترويسات مثل `Cache-Control: no-cache` و `Pragma: no-cache`. إذا لاحظ مسؤولو مراقبة الشبكة (SOC) سيلاً من الطلبات المتتالية القادمة من نفس عنوان IP وتحمل نفس المعرّف مع تغير طفيف في الحمولات دون تحميل الموارد المرافقة (صور، ملفات CSS)، يتم اكتشاف نشاط الفحص اليدوي فوراً.
* **تخفيف البصمة أثناء اختبار Repeater:**
  * مطابقة ترويسات `User-Agent` و `Accept` مع حركة المرور الطبيعية للمتصفح.
  * تجنب إرسال طلبات متتالية بسرعة آلية مفرطة تجنباً لإثارة قواعد WAF أو أنظمة كشف التسلل (IDS/IPS).
