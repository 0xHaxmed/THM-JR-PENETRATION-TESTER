# Additional Technical Notes: Passive Reconnaissance
## ملاحظات تقنية ميدانية وتعمق هندسي في الاستطلاع السلبي

---

### 1. المعمارية الداخلية لبروتوكول WHOIS والتحول نحو RDAP

* **البروتوكول التقليدي (RFC 3912):**
  يعمل WHOIS على المنفذ `43/TCP`. يرسل العميل اسم النطاق متبوعاً بسطر جديد (`CRLF`)، ويستقبل نصاً خاماً غير منظم (Unstructured Text) يختلف شكله وتنسيقه من مسجل إلى آخر.
* **الفرق بين السجلات النحيفة والسميكة (Thin vs. Thick Registries):**
  * **Thin Registry (مثل نطاقات `.com` و `.net` المدارة بواسطة VeriSign):** يحتفظ السجل المركزي فقط باسم المسجل (Registrar) وخوادم الأسماء (Name Servers). لاستخراج بيانات المالك، يجب على العميل إرسال استعلام ثانٍ إلى خادم الـ WHOIS الخاص بالمسجل المباشر (مثل Namecheap).
  * **Thick Registry (مثل نطاقات `.org` و `.info`):** يحتفظ السجل المركزي بكافة بيانات المالك وجهات الاتصال الفنية والإدارية في نفس المكان.
* **البروتوكول الحديث (RDAP - Registration Data Access Protocol):**
  بسبب اللوائح الأوروبية لحماية البيانات (GDPR) وضعف أمان بروتوكول WHOIS، اعتمدت منظمة ICANN بروتوكول RDAP (RFC 7480) الذي يعمل عبر بروتوكول HTTPS ويُرجع البيانات بصيغة JSON مهيكلة ويدعم المصادقة وتشفير البيانات.

### 2. ميكانيكا استعلامات DNS المتقدمة عبر أداة `dig`

تعتبر أداة `dig` الخيار القياسي للمحترفين بفضل قدرتها على التحكم الدقيق في حزم الاستعلام:

#### أهم الخيارات والأوامر الميدانية:
```bash
# 1. الاستعلام المباشر عبر خادم DNS محدد (مثل Google DNS 8.8.8.8)
dig @8.8.8.8 tryhackme.com A

# 2. تتبع مسار الاستعلام الهرمي بالكامل من خوادم الجذر Root Servers حتى الخادم الموثق
dig tryhackme.com +trace

# 3. عرض الإجابة الصافية فقط بدون ترويسات أو تعليقات إضافية
dig tryhackme.com +noall +answer

# 4. الاستعلام العكسي لتحويل عنوان IP إلى اسم نطاق (PTR Record)
dig -x 104.26.11.231 +short

# 5. محاولة نقل النطاق الكامل (Zone Transfer - AXFR) لاكتشاف كافة السجلات
dig @ns1.target.com target.com AXFR
```

### 3. شفافية الشهادات الرقمية (Certificate Transparency - CT Logs)

في كثير من الأحيان، تفشل أدوات استعلام الـ DNS في كشف النطاقات الفرعية السرية (مثل `dev-portal.company.com` أو `internal-api.company.com`) لأنها غير مدرجة في قوائم التخمين الشائعة.

**سجلات شفافية الشهادات (CT Logs):**
وفق معايير متصفحي الويب الحديثة (Chrome, Firefox)، تُلزم جهات إصدار الشهادات الرقمية (Certificate Authorities - CAs) بنشر سجل عام مشفر لكل شهادة SSL/TLS يتم إصدارها لأي نطاق في العالم!
* **الاستغلال الاستخباري:**
  يمكن لمختبر الاختراق استعلام هذه السجلات العامة مجاناً عبر منصات مثل:
  * `https://crt.sh/?q=%.tryhackme.com`
  * بمجرد البحث، تظهر كافة النطاقات الفرعية التي استخرجت لها الشركة شهادة SSL عبر التاريخ، بما في ذلك الخوادم التجريبية وخوادم الـ VPN الداخلية!

### 4. كشف عنوان الـ IP الحقيقي وتجاوز حماية Cloudflare (Origin IP Discovery)

عندما يستخدم الهدف خدمات حماية الـ CDN مثل Cloudflare، فإن عنوان IP الذي يظهر في استعلامات DNS العادية (A Records) هو عنوان خادم البروكسي التابع لـ Cloudflare، وليس خادم الشركة الحقيقي.

#### تقنيات سلبية لاكتشاف عنوان الـ IP الأصلي (Origin IP):
1. **فحص سجلات الـ MX (خوادم البريد):**
   غالباً ما يتم توجيه البريد لخادم غير محمي بـ Cloudflare. فحص سجلات `MX` قد يكشف خادماً يقع في نفس نطاق الـ IP التابع لخادم الويب الرئيسي.
2. **سجلات DNS التاريخية (Historical DNS Data):**
   استخدام منصات مثل `ViewDNS.info` أو `SecurityTrails` لمعرفة عنوان الـ IP الذي كان يرتبط به النطاق قبل تفعيل خدمة Cloudflare؛ فكثير من الشركات لا تغير خوادمها بل تضع Cloudflare أمامها فقط!
3. **شهادات SSL على مستوى الإنترنت (Censys / Shodan Search):**
   البحث في محرك Censys عن الشهادة الرقمية الصادرة لاسم النطاق؛ فإذا كان الخادم الأصلي يقدم الشهادة مباشرة على منفذ 443 دون تقييد الجدار الناري لحزم Cloudflare، يظهر الـ IP الحقيقي فوراً.
